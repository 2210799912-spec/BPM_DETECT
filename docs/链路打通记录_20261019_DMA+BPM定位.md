# DMA 真正跑通 + BPM 问题定位（2026-10-19 实证）

## 一、DMA 为什么之前一直"看似有反应却不通"——终于找到根因

之前所有症状（数据一样 / swing恒定 / 通道永不idle / transfer被拒）追溯到 **一个被长期忽略的参数：transfer 长度 vs 上游 axis_data_fifo 深度**。

### 铁证（扫描 LEN 测试 dma_sweep_len）
| LEN | idle | same | swing | 结论 |
|-----|------|------|-------|------|
| 128 | -1   | 0    | [461]       | transfer被拒(通道没空) |
| **256** | **2** | **0** | [0,559] | ✅ idle且刷新 |
| **512** | **2** | **0** | [530,608] | ✅ idle且刷新 |
| **1024**| **1** | **0** | [646,690] | ✅ idle且刷新 |
| 2048/4096/8192 | (未跑/历史) | | | 历史证明永不idle |

### 根因机制
- BD(design_1.tcl L349-350)里 **axis_data_fifo_0 是默认深度 512**（未改配置）。
- segment_stream 顶层逻辑（segment_stream_v1_0.v）：
  ```verilog
  assign m_axis_tvalid = s_axis_tvalid && (count != 0);  // count>0 才放行
  assign m_axis_tlast  = count == 1;                     // 第N个字带TLAST
  // 写REG0=N -> count=N；每透传1字count-1；count=0关门
  ```
- **transfer长度设8192/32768 >> fifo深度512** → DMA永远等不满BTT → 通道永不idle → 后续transfer被拒 → buffer从没被新数据填充（读到旧数据）。

### 解法（已验证，DMA真通）
**transfer块长必须落在fifo深度附近**，让BTT能被填满→DMA完成→idle→可循环复用。
采用 **LEN=512**（或256/1024），每帧连采多个512块拼接成完整波形。
关键代码：
```python
LEN = 512
buf = allocate(shape=(LEN,), dtype=np.uint32)
dma.recvchannel.start()      # 只启动一次
def grab_block():
    dma.recvchannel.transfer(buf)
    buf.flush()               # 写回cache
    seg.mmio.write(0x00, LEN) # 重武装segment放行LEN字
    time.sleep(0.05)          # 固定等待(不要等idle, 但此处长度足够使DMA真idle)
    buf.invalidate()          # 失效cache, 读到DMA写入的最新数据
    return np.asarray(buf).copy()
def grab_wave():
    ch=[]
    for _ in range(B_PER):
        ra=grab_block(); x=(ra[::2]^0x800000).astype(np.int32)-0x800000
        ch.append(x)
    return np.concatenate(ch)  # 拼B_PER个块成完整波形
```

## 二、BPM 恒定 240 —— 问题在哪？（不在寄存器！）

### 寄存器读法是对的（经驱动头确认）
- XBPM_DETECT_CTRL_ADDR_REGS_BASE = 0x40（xbpm_detect_hw.h L14）
- bpm_detect.h: REG_TOTAL=0, REG_BPM=6, REG_DEBUG=7, REG_RATIO=8
- 所以实际地址：
  - BPM    @ 0x40+6*4 = **0x58**  ✓
  - DEBUG  @ 0x40+7*4 = **0x5C**  ✓
  - RATIO  @ 0x40+8*4 = **0x60**  ✓
- **寄存器偏移没问题，与之前一致。**

### 真正原因 = 算法参数 REFRACTORY 把 BPM 钳制在上限
- bpm_detect.h: `FS_HZ=60418, BPM_CONST=3625080, REFRACTORY=15104`
- 最大可报告 BPM = BPM_CONST / REFRACTORY = 3625080/15104 = **240.0**
- 节拍器触发间隔 ≤ REFRACTORY(15104样本) 时，instant_bpm ≥ 240 → **被钳制在240上限**。
- peaks正常递增(0→40)，说明检测生效，只是 BPM 撞到 REFRACTORY 上限。

### 修复方向（若要让真实节拍显示出来）
- 增大 REFRACTORY（如 30000 → 上限120BPM；或 24000 → 上限150BPM），需改 bpm_detect.h + 重新 C-sim + 综合 + 换新IP。
- 或先确认节拍器实际BPM，再反推REFACTORY取值：REFRACTORY < FS*60/目标BPM。

## 三、结论
- **DMA 已跑通（块长≤fifo深度512）**，整条 adau→fifo→segment→bpm→DMA 数据通路 OK。
- **BPM=240 不是寄存器问题，是 REFRACTORY 参数把 BPM 钳制在上限**。若要真实读数需调大 REFRACTORY。
