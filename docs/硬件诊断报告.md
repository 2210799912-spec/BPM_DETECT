## 第一根因：采集碎片化，占空比只有 18.4%（v2 新发现，致命）

这是真正让 BPM 永远测不出来的原因，而且**与算法、与 IP 完全无关**——是 notebook 的采集节拍造成的。

### 机制

`grab_block()` 的时序：

```python
LEN = 512
ra = ...                      # 512 个 32bit 字
return (ra[::2] ^ ...)        # 取左声道 -> 256 点
...
time.sleep(0.03)              # 30ms
```

- 每块音频内容：256 样本 = **5.53 ms**
- 每块占用墙上时间：**30 ms**（sleep 期间 DMA 未 arm）
- 每块丢弃：1133 样本 = **24.47 ms**
- **占空比 d = 5.53/30 = 18.43%**

`design_1.tcl:361` 显示 `bpm_detect_0/audio_out → axi_dma_0/S_AXIS_S2MM`。DMA 直接寄存器模式（`c_include_sg=0`）在未 arm 传输时 `TREADY=0`，反压逐级上传：

```
DMA TREADY=0 → audio_out.write 阻塞 → audio_in.read 阻塞
            → segment_stream 停 → axis_data_fifo 填满 → adau1761 停
```

**codec 在这 24.47ms 里产生的样本被丢弃，不是缓存。** 硬件收到的是一条"时间被压缩"的拼接流。

### 数学后果：时间轴被压缩 5.43 倍

`bpm_detect` 的 `cnt` 每收到一个样本才 +1。硬件视角的时间 = 真实时间 × d：

```
压缩倍数 = 1/d = 5.43x
表观 BPM = 真实 BPM × 5.43
```

| 真实 BPM | 真实拍间隔 | 表观 BPM | 表观间隔(样本) | 过 REFRACTORY(15433)? | 结果 |
|---|---|---|---|---|---|
| 60 | 46300 | 325.5 | 8533 | **否** | 全被不应期掐死 → BPM=0 |
| 90 | 30867 | 488.3 | 5689 | **否** | 全被不应期掐死 → BPM=0 |
| 120 | 23150 | 651.1 | **4267** | **否** | 全被不应期掐死 → BPM=0 |
| 150 | 18520 | 813.9 | 3413 | **否** | 全被不应期掐死 → BPM=0 |
| 180 | 15433 | 976.6 | 2844 | **否** | 全被不应期掐死 → BPM=0 |

**在 18.4% 占空比下，60~180 BPM 全区间都测不出来。** 真实 120BPM 的表观间隔只有 4267 样本，不到 REFRACTORY 的 1/3，每一个真拍都被不应期掐死。

### m120.npy 里实测到的 2 次触发，根本不是节拍

用真实数据跑镜像，`SHIFT=0, SIL=2^26, ADAPT=16`（当前参数）：触发 2 次，读出 **95.2 BPM**。

拆开这 2 次的间隔：

| 间隔(样本) | 折成块数 | 对应墙上时间 | 换算真实 BPM |
|---|---|---|---|
| 16004 | 62.5 块 | 1.88 s | **32.0** |
| 29035 | 113.4 块 | 3.40 s | **17.6** |

真实 BPM 只有 32 / 18 —— 不是音乐节拍，是随机噪声峰碰巧满足了局部峰 + 不应期条件。**硬件把它们读成 173.6 / 95.7 BPM。这就是"读数与音乐内容无关"的铁证。**

### "静音也锁 176.3" 的真正解释（修正 v1）

v1 说是 `REFRACTORY` 零容差导致丢拍腰斩。**真实数据显示主因不同**：

`bin 0` 覆盖间隔 `[15433, 16073)` 样本，对应表观 BPM `[172.8, 180.0]`。碎片化之后，任何"勉强通过 REFRACTORY"的**最小可能间隔**都必然落进 bin 0。所以静音噪声的偶发触发**必然**读出 ~176.3。

**176.3 不是算法 bug，是采集 bug 在输出端的投影。**

### 修复

| LEN | 左声道点 | 块音频时长 | sleep 需小于 | 占空比 | 120BPM 可测? |
|---|---|---|---|---|---|
| 512（现状） | 256 | 5.53ms | 5.53ms | 15.6%（sleep=30ms 时） | 否 |
| 512 | 256 | 5.53ms | **1.0ms** | **84.7%** | **是** |
| 2048 | 1024 | 22.12ms | 1.0ms | **95.7%** | 是 |
| 8192 | 4096 | 88.47ms | 1.0ms | **98.9%** | 是 |
| 16384 | 8192 | 176.93ms | 1.0ms | **99.4%** | 是 |

你笔记写"LEN≤512 才能 idle+刷新"——那是 DMA 直接寄存器模式的长度约束（与 `c_sg_length_width=26` 无关）。若无法加大 LEN，**必须把 `sleep(0.03)` 降到 <5.53ms，或改成轮询 DMA idle 位**。这是成本最低、见效最快的一步，且不碰硬件。

## 第二根因：数据时长不足（v2 新发现）

`m120.npy` 只有 **1.443 s** 音频内容，但算法需要：

| 环节 | 所需样本 | 时长 |
|---|---|---|
| 包络窗填充（ENV_WIN=1024） | 1024 | 22.1 ms |
| **base 慢均收敛**（BASE_SHIFT=17，时间常数 2^17） | 131072 | **2.83 s** |
| 看门狗周期（WATCHDOG=2×46300） | 92600 | 2.00 s |
| 120BPM 拍间隔 | 23150 | 500 ms |

**数据长度（1.44s）短于 base 收敛时间（2.83s）**，也短于看门狗周期（2.00s）。名义 120BPM 在 1.44s 内只有 **2.9 拍**，而算法需要 3~4 拍投票才能定 bin —— 统计上不可能锁定。

另外 66816 = 256 × 261，采集墙上时间 = 261 × 0.03 = **7.83 s**，但只留下 1.44s 音频，**82% 被丢弃**。

重采要求：**至少 8~10 秒连续音频**，且占空比接近 100%。

## 第三根因：MIC 收音电平过低（−59.7 dBFS）

| 指标 | 实测值 |
|---|---|
| \|x\| 最大 | **8666** |
| RMS | 471.1 |
| 满量程占比（24bit） | 0.1033% = **−59.7 dBFS** |
| int16 回绕门槛 32767 已用 | 26.4% → **未触发回绕** |

这直接**推翻 v1 的"16 位截断回绕是第一根因"**：在当前 MIC 配置下幅值远低于门槛，`|x|>32767` 的样本数是 **0/66816**，回绕根本没发生。

但电平过低本身是问题：`env_sum` 峰值只有 1.539e+09，而 `SILENCE_E_MIN=2^26=6.71e+07` 虽然勉强能过，信噪余量极小。用真实数据实测：

| 配置 | 触发数 | 票数 | BPM |
|---|---|---|---|
| 现状 SHIFT=0, SIL=2^26, ADAPT=16 | 2 | 2 | 95.2（噪声峰，非节拍） |
| 仅修截断 SHIFT=8 | **0** | 0 | 0.0 |
| SHIFT=8 + SIL=2^12 | 3 | 3 | 133.1（仍非节拍） |
| SHIFT=8 + SIL=0 + ADAPT=8 | 4 | 4 | **176.3** |

注意第 2 行：**改成 SHIFT=8 后触发数直接归零**。因为真实信号幅值只有 8666，右移 8 位后只剩 33，能量被削弱 65536 倍，全部低于 `SILENCE_E_MIN`。

**结论：在 MIC 当前增益下，`SAMPLE_SHIFT` 0→8 不但不是修复，反而会让系统完全失效。必须先解决增益问题。**

### 与 v1 结论的关系

v1 发现的 16 位截断隐患**依然真实存在**，只是当前没被触发。它的爆发条件是：改用 LINE_IN、提高 GAIN、或音源更响，使 `|x| > 32767`。这正好解释你记录的**"音量越大越容易误出大 BPM 又消失"**——那个现象发生在 louder 场景，此时回绕确实启动了。

正确修法不是简单 `SHIFT=8`，而是**先把信号拉到合理电平，再配合 SHIFT**：目标是让 `|x|` 落在 3276~32767 之间（既够大、又不触发回绕）。

### bin 索引：穷举 30868 个取值验证通过

RTL 把 `/640` 优化成倒数乘法，中间量只有 15 位：

```
trunc_ln161 = event_interval[14:0]                    (15位截断)
add_ln161   = trunc_ln161 + 15'd17335                  (17335 = -15433 补码)
mul_ln161   = add_ln161 * 31'd52429                    (ceil(2^25/5), 因 /640 = /5 >>7)
tmp_4       = mul_ln161[30:25]                         (>>25, 取 6 位作 bin)
```

穷举 `[15433, 46300]` 全部 30868 个 interval：**RTL 与源码语义完全一致，零 mismatch**；中间积最大 1.618e9 < 2^31 未溢出；最大 bin=48 < 64 未越界；其中 13533 个取值 interval ≥ 32768（会触发 15 位截断）全部仍正确。

原理：interval 跨度 `46300 − 15433 = 30867 < 2^15`，故 `(interval[14:0] − 15433) mod 2^15` 恒等于真值。**侥幸但正确。**

### ⚠️ 悬崖：改 REFRACTORY 的安全边界

上面那个"侥幸"余量只有 `32768 − 30867 = 1901` 样本：

| REFRACTORY | 最高可测 BPM | interval 跨度 | 15 位截断 |
|---|---|---|---|
| 15433（现值） | 180.0 | 30867 | 安全 |
| 14531 | 191.2 | 31769 | 安全 |
| **13890（建议值）** | **200.0** | **32410** | **安全** |
| 13000 | 213.7 | 33300 | **越界，bin 索引算错** |
| 12861 | 216.0 | 33439 | **越界** |
| 12000 | 231.5 | 34300 | **越界** |
| 11573（曾用的 BPM_CONST/240） | 240.0 | 34727 | **越界** |

**临界点：REFRACTORY 最小只能取 13533（= 46300 − 32767），对应最高可测 205.3 BPM。**

跨度一旦 ≥ 32768，15 位有符号中间量翻成负数，bin 索引**静默算飞**——不报错、不告警，只读出离谱 BPM。你之前用过的 `11573` 正落在越界区。

配套约束：`bpm_table` ROM 按 `BPM_LO_INTERVAL` 预计算，RTL 里 `15'd17335` 与 ROM 内容同源。改 REFRACTORY 必须**同步重算整张 ROM**，漏改一个就全表错位。

## 仍然成立的 v1 结论

### REFRACTORY 与 180BPM 零容差

```
REFRACTORY = 15433
180 BPM 真值间隔 = 60 × 46300 / 180 = 15433.33 样本
```

触发条件 `(cnt-1-last_peak) >= REFRACTORY`，真值间隔 **15433** 与门限 **15433** 完全相等，**零容差**。任何抖动让间隔落到 15432 就被丢弃 → 每两拍丢一拍 → 读数腰斩到 87.5（`BPM_TABLE[25]=22396` → 87.484 BPM，间隔≈2×15433）。

这条在真实数据下依然成立，但**优先级低于碎片化问题**——因为碎片化让所有 BPM 都测不出来，根本轮不到 180 边界暴露。

### 验收标准要分清两种 176.3

| 现象 | 性质 | 修复 |
|---|---|---|
| 180 读成 **176.3** | ROM 量化精度（bin 宽 640 样本），**不是 bug** | 只能缩小 `HIST_BINW` 加密桶数 |
| 180 读成 **87.5** | REFRACTORY 零容差丢拍 | 改 REFRACTORY=13890 |
| **静音锁 176.3** | **碎片化采集的投影**（v2 修正） | 改 sleep / 加大 LEN |

### 0x10~0x38 六个 RW 寄存器是空壳

`xbpm_detect_hw.h` 显示 `0x10~0x38` 是 Read/Write（`regs_0~regs_5`），看着像能在线调参。实测 RTL 出现次数：

| 寄存器 | RTL 出现次数 | 实际用途 |
|---|---|---|
| regs_0 ~ regs_5 | 3（仅声明 + 例化端口） | **未接入数据通路** |
| regs_6 (0x40) | 4 | BPM 输出（float） |
| regs_7 (0x50) | 1 | update_cnt |
| regs_8 (0x60) | 1 | env_sum 低 32 位 |

源码印证：`regs[REG_TOTAL]` 只在 `#ifndef __SYNTHESIS__` 分支使用，综合时 `local_stop = 0xFFFFFFFF`。**所有算法参数都是编译期常量，改任何一个都要重跑 HLS。**

建议：既然要重跑 HLS，顺手把 `ADAPT_FACTOR`、`SILENCE_E_MIN`、`REFRACTORY` 接到 `regs_1~regs_3`，上板可用 notebook 在线扫参数——省下大量迭代时间。

### 网页波形与硬件信号不同源

notebook 用 `^0x800000` 做 24bit 符号扩展画到 canvas，硬件吃的是低 16 位。当前 MIC 电平下两者数值相同（因为没触发回绕），但**loud 场景下会分叉**，届时浏览器波形对调试毫无参考价值。

## 修正后的推进顺序

**v1 的第 3、4 步（改 ADAPT / 换阈值机制）暂缓**——真实数据证明那不是当前的瓶颈。

1. **改采集节拍（最高优先级，不碰硬件）**
   `sleep(0.03)` → 轮询 DMA idle，或降到 <5ms；条件允许则加大 LEN。
   目标：占空比从 18.4% 提到 >95%。**这一步不做，后面所有调参都是无效的。**

2. **重采一份合格数据**
   8~10 秒连续音频、占空比 >95%、幅值 `|x|` 落在 3276~32767。
   分别采：静音 / 120BPM 鼓点 / 连续音乐 / 180BPM 鼓点。

3. **先解决 MIC 增益，再谈 SAMPLE_SHIFT**
   当前 −59.7dBFS 太低。提 GAIN 或等 LINE_IN 线到货。
   ⚠️ **不要在增益没解决前改 `SHIFT=8`**——实测会让触发数直接归零。

4. **用新数据在 Python 镜像里标定阈值**
   `_mirror_probe.py` 的 `detect()` 参数全可调，不上板就能预判 ADAPT / SILENCE_E_MIN 的可用窗口。**只有基于合格数据的标定才有意义**，v1 那种基于合成信号的标定已被证明无效。

5. **一次性改 HLS 源码**（确需重跑时）
   - 阈值机制（依据第 4 步标定结果）
   - `REFRACTORY` / `BPM_LO_INTERVAL` → 13890 + 同步重算 ROM（⚠️ 下限 13533）
   - `SAMPLE_SHIFT`（依据第 3 步的增益结果决定）
   - 参数接到 `regs_1~regs_3` 做运行时可调

6. **补 tb.cpp 的真实信号用例**
   现有 `peak_at()` 是阶跃注入（瞬时 dx = 全幅值），真实鼓点是振荡波形（最大 dx = amp×2πf/FS，差 82 倍）。加入振荡型用例，并覆盖 loud 场景（`beat_amp` 提到 0x200000 以上）以暴露 16 位回绕。
